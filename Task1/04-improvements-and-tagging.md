# 4) Что улучшить: защита данных, тегирование, меры и инструменты

Цель: снизить риск утечек и неправомерного доступа к медкартам/PII, обеспечить масштабирование (филиалы, новые сотрудники, клиентский портал/мобильное приложение, интеграции).

## 4.1. Список данных для защиты и способы защиты

Ниже — рекомендуемая базовая матрица «категория данных → способы защиты».

### Confidential‑Health (медицинские данные)

- **Шифрование**: обязательное шифрование «на хранении» (БД/объектное хранилище) и «в транзите» (TLS).
- **Обезличивание** (для аналитики/озера данных): токенизация или псевдонимизация идентификаторов пациента; отделение ключей/маппингов.
- **Обфускация/маскирование** (в UI и выгрузках): скрытие частей значений для не‑медролей; «need-to-know».

### Confidential‑PII (ПДн)

- **Шифрование**: на хранении/в транзите; шифрование бэкапов.
- **Обфускация/маскирование**: телефон/email/адрес; частичное отображение по ролям.
- **Обезличивание**: для BI/ML/AI — токенизация/хеширование + контролируемые справочники.

### Confidential‑Finance (платежи/договоры/чеки)

- **Шифрование**: документы/сканы договоров, платёжные события и журналы.
- **Маскирование**: в интерфейсах для ролей без финансового допуска.
- **Обезличивание**: в аналитике — отделение PII от транзакционных агрегатов.

## 4.2. Механизм тегирования данных (концепт)

Тегирование нужно, чтобы в будущем:
- автоматически проверять релизы на работу с чувствительными данными;
- гарантировать корректные политики доступа и логирование;
- включать DLP/маскирование/ретенцию по тэгам.

### 4.2.1. Модель тегов

Рекомендуемая схема тегов (пример):

- `data.class`: `public | internal | confidential_pii | confidential_health | confidential_finance`
- `data.subject`: `patient | employee | vendor`
- `data.domain`: `appointments | emr | lab | billing | inventory | comms`
- `data.retention`: `P1Y | P3Y | P5Y | ...` (или ссылка на политику)
- `data.legal`: `152FZ | medical_secret | ...` (по требованиям РФ/внутренним политикам)
- `data.masking`: `none | partial | full` (как показывать по умолчанию)

### 4.2.2. Где хранить теги

- **На уровне схемы данных** (БД): теги на столбцах/полях (data catalog / metadata store).
- **На уровне событий**: события доменов несут `data.class` и `data.domain` в метаданных.
- **На уровне файлов** (объектное хранилище): теги объекта + связь с сущностью (patient_id, document_id).

### 4.2.3. Применение тегов (policy enforcement)

- **Доступ**: RBAC/ABAC политики читают теги и атрибуты запроса (роль, филиал, отношение к пациенту, контекст).
- **Логи**: обязательное логирование всех обращений к `confidential_*` с корреляцией (user_id, patient_id, action, purpose).
- **Маскирование**: UI/репорты/экспорты по `data.masking`.
- **Ретенция/удаление**: политики хранения по `data.retention`, поддержка запроса на прекращение обработки.

## 4.3. Набор мер, чтобы обеспечить конфиденциальность в потоках

### Архитектурные меры

- **Декомпозиция по доменам данных**: отдельно домены записи/расписания, EMR (медкарта), лаборатория, биллинг.
- **Единый ID пациента и контроль отношений**: привязка действий к пациенту, запрет «чужих» данных.
- **API‑контракты с минимизацией**: отдельные DTO/Scopes для ролей и каналов (сотрудник vs пациент).

### Управление доступом

- **RBAC + ABAC**: роли (врач/ресепшен/кассир/бухгалтер/склад/IT) + атрибуты (филиал, лечащий врач, назначение, контекст).
- **MFA для привилегированных ролей**, отдельные админ‑учётки, PAM‑подход.
- **Принцип минимальных привилегий** и регулярная реквалификация доступов.

### Техническая защита данных

- **Шифрование**: TLS везде, шифрование хранилищ/бэкапов, KMS/HSM‑подход для ключей.
- **Разделение хранилищ**: документы/сканы в объектном хранилище с ACL и аудитом; уход от общих папок.
- **Секреты**: централизованное хранение секретов, ротация.

### Контроль утечек и коммуникаций

- **DLP/классификация** для почты и файлов (политики для `confidential_*`).
- **Запрет/контроль внешней отправки** вложений с медданными, карантин/шифрование.

### Наблюдаемость и аудит

- **Аудит доступа к данным**: события чтения/изменения/экспорта для чувствительных сущностей.
- **SIEM/алерты**: аномалии (массовые выгрузки, доступ вне смены, гео/устройства, необычные запросы).

### Жизненный цикл данных

- **Ретенция**: сроки хранения по классам данных, политики архивирования.
- **Удаление**: процедуры безопасного удаления, поддержка «прекратить обработку» по запросу.

## 4.4. Инструменты (классы решений, без привязки к вендору)

- **IAM/SSO**: IdP + MFA + RBAC/ABAC (политики).
- **KMS/HSM**: управление ключами, ротация, разграничение.
- **DLP**: для почты/файлов/эндпоинтов.
- **Data Catalog / Metadata store**: хранение тегов, lineage, классификация.
- **Audit log pipeline**: централизованный сбор аудита → SIEM/мониторинг.
- **Policy engine**: централизованные правила доступа/маскирования (в сервисах/шлюзах).

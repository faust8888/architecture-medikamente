# 2) Стратегия шифрования данных: At Rest и In Transit

## 2.1. Цели стратегии

- **Конфиденциальность**: исключить чтение данных при компрометации канала/диска/бэкапа.
- **Целостность**: обеспечить защищённый обмен и неизменяемость журналов (audit).
- **Управляемость**: централизованные ключи, ротация, минимизация доступа к ключам.
- **Скалируемость**: одинаковые правила для новых сервисов/интеграций («secure-by-default»).

## 2.2. Encryption In Transit (передача)

### Базовые правила

- **TLS 1.2+ / 1.3** на всех HTTP(S) каналах.
- **mTLS** для сервис‑к‑сервису в доверенной сети (service mesh или взаимная TLS на уровне клиентов).
- **Certificate management**: централизованная выдача и ротация сертификатов (короткий TTL).
- **Запрет небезопасных протоколов**: SMB/почта/вложения для передачи `Confidential‑Health` как «канал по умолчанию».

### По ключевым потокам

| Поток | Что передаём | Требование |
|---|---|---|
| Мобильное приложение/ЛК ↔ API Gateway | PII, запись, просмотр своих данных | TLS + HSTS, pinning опционально |
| Портал сотрудников ↔ API Gateway | PII/PHI по ролям | TLS, MFA, устройства/контекст |
| API Gateway/BFF ↔ доменные сервисы | запросы/ответы доменов | TLS внутри, желательно mTLS |
| Домены ↔ Event Bus | события доменов | TLS; шифрование канала + ACL топиков |
| Lab Service ↔ внешняя лаборатория | результаты анализов/статусы | **mTLS**, контрактная минимизация, allow‑list IP |
| Billing ↔ ККМ/фискализация | фискальные события/чеки | TLS (или защищённый канал провайдера), сегментация сети |
| Доставка логов/аудита → SIEM | события безопасности | TLS + взаимная аутентификация агента |

### Практики минимизации

- В уведомлениях/сообщениях (email/SMS/push) — **никаких медданных** и минимум PII (например, «У вас запись» без диагноза).
- Междоменные вызовы — только необходимые DTO (не «вся карточка пациента»).

## 2.3. Encryption At Rest (хранение)

### Базовые правила

- **Шифрование по умолчанию** для всех хранилищ: БД, объектное хранилище, очереди (если поддерживается), диски.
- **Ключи не хранятся рядом с данными**: ключи в `KMS/HSM`, доступ по ролям.
- **Разделение ключей по доменам/классам**: минимум — ключи для `EMR` отдельно от `Appointments/Billing`.
- **Ротация ключей**: плановая + принудительная при инцидентах.
- **Шифрование бэкапов**: обязательно, с отдельными ключами и контролем доступа.

### Где именно шифровать

| Компонент | Данные | Механизм ENC@REST |
|---|---|---|
| `EMR DB` | Confidential‑Health + PII | TDE/volume encryption + field‑level encryption для особо чувствительных полей (опционально) |
| `Lab DB` | результаты/метаданные | ENC@REST, отдельный ключ домена Lab |
| `Appointments DB` | запись/контакты | ENC@REST |
| `Billing DB` | финансы/документы | ENC@REST, повышенные требования к аудит‑логам |
| `Object Storage` | документы/сканы | server‑side encryption + KMS‑ключи, ACL по объектам, версии |
| `Audit Log` storage | события доступа | ENC@REST + WORM/immutability (если возможно) |
| `Backups` | все домены | ENC@REST + отдельный keyring + изоляция доступа |

### Дополнительно для «In Use»

Хотя задание про at rest/in transit, важно зафиксировать минимум для in‑use:
- минимизация секретов в памяти, запрет логирования PHI/PII,
- защита рабочих станций (disk encryption), экраны, запрет локальных копий.

## 2.4. Управление ключами (KMS/HSM) — обязательный слой

Минимальные требования:

- **KMS** как единый сервис ключей для шифрования хранилищ и токенизации.
- **Разграничение доступа к ключам**: разные роли для операций encrypt/decrypt, раздельные админ‑права.
- **Аудит использования ключей**: кто и когда выполнял decrypt, алерты на аномалии.
- **Envelope encryption**: приложения работают с data‑keys, master‑keys остаются в KMS/HSM.

## 2.5. Gaps As‑Is (что сейчас не покрыто)

По текущему описанию As‑Is:
- Excel/сканы на общем диске: отсутствует гарантированное ENC@REST на уровне данных, нет KMS/ключей, нет аудит‑логики «по сущностям».
- Передача через почту/вложения: нет гарантий шифрования и контроля распространения; нет DLP.
- Интеграции «ручные» (лаборатория): нет mTLS, нет контрактной минимизации и контроля доступа.

## 2.6. Итог: правило «secure-by-default»

Для всех новых сервисов/интеграций:
- канал только по TLS/mTLS,
- хранение только в шифрованных хранилищах,
- ключи только через KMS/HSM,
- теги данных определяют политики доступа/аудита/экспорта.

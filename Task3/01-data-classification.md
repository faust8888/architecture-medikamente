# 1) Какие данные нужно защищать — классификация

## 1.1. Ось классификации (как требование задания)

Классифицируем данные по:

- **Состоянию**:  
  - **At Rest** — хранение (БД, файловые/объектные хранилища, бэкапы, логи).  
  - **In Transit** — передача (API, интеграции, репликации, почта/уведомления).  
  - **In Use** — обработка (память приложений, кэши, рабочие станции).
- **Чувствительности** (data class): `Public` / `Internal` / `Confidential‑PII` / `Confidential‑Health` / `Confidential‑Finance`.
- **Профилю риска**: вероятность утечки/компрометации и ущерб (репутационный/финансовый/регуляторный).
- **Каналу/поверхности**: внешний интернет, внутренняя сеть, партнёрская интеграция, клиентские устройства.

## 1.2. Классы данных (минимальный набор)

### Public

Не содержит ПДн/медданных. Пример: публичные описания услуг.

### Internal

Служебная информация без ПДн: справочники услуг без привязки к пациенту, тех.метрики без идентификаторов.

### Confidential‑PII (ПДн)

- ФИО, дата рождения, контакты, адрес, идентификаторы пациента.
- Любые ключи/токены, позволяющие связать запись/событие с конкретным человеком.

### Confidential‑Health (медтайна / спецкатегории ПДн)

- диагнозы, назначения, результаты анализов, медкарта, прикреплённые файлы/сканы.

### Confidential‑Finance (договоры/платежи/фискальные данные)

- договоры, счета, статусы оплат, чеки/фискальные документы (в части, где присутствуют идентификаторы и/или ПДн).

## 1.3. Что именно защищаем в To‑Be (с привязкой к архитектуре)

Ниже — «объекты защиты» и типичные места/состояния.

### Домен Appointments (запись/расписания)

- **Данные**: запись на приём (PII + расписание), иногда комментарии.  
- **At Rest**: `Appointments DB`, бэкапы.  
- **In Transit**: клиент ↔ API (интернет), BFF ↔ сервис, события в шину.

### Домен EMR (медкарта)

- **Данные**: `Confidential‑Health` + PII.  
- **At Rest**: `EMR DB`, объектное хранилище документов, бэкапы, журналы аудита.  
- **In Transit**: UI ↔ EMR API, EMR ↔ Lab, EMR ↔ Docs.

### Домен Lab (анализы)

- **Данные**: результаты анализов (PHI) + идентификаторы пациента.  
- **At Rest**: `Lab DB`, файлы результатов.  
- **In Transit**: интеграция с внешней лабораторией.

### Домен Billing (оплаты)

- **Данные**: транзакции, чеки, договоры (частично PII).  
- **At Rest**: `Billing DB`, журналы, бэкапы.  
- **In Transit**: интеграция с ККМ/фискальным контуром, внутренние API.

### Документы (сканы/вложения)

- **Данные**: сканы договоров, анализов, заключений (часто `Confidential‑Health`).  
- **At Rest**: объектное хранилище + метаданные.  
- **In Transit**: выдача ссылок/скачивание, загрузка файлов.

### Аудит/наблюдаемость

- **Данные**: логи доступа к чувствительным сущностям, события безопасности.  
- **At Rest**: хранилище логов/SIEM, архивы.  
- **In Transit**: доставка логов/трейсов.

## 1.4. Обоснование необходимости защиты (коротко)

- `Confidential‑Health` — максимальная чувствительность: утечки → высокий регуляторный и репутационный ущерб. Требует строгого шифрования, минимизации, аудита.
- `Confidential‑PII` — высокий риск злоупотреблений (фрод/социнж), требует шифрования и маскирования.
- `Confidential‑Finance` — риск мошенничества и инцидентов, важна целостность и неизменяемость логов.

## 1.5. Минимальная матрица «класс → требования шифрования»

| Класс данных | At Rest | In Transit |
|---|---|---|
| Public | опционально | TLS желательно |
| Internal | ENC@REST желательно (по умолчанию) | TLS обязательно внутри/снаружи |
| Confidential‑PII | **ENC@REST обязательно** + KMS | **TLS обязательно**, mTLS для интеграций |
| Confidential‑Health | **ENC@REST обязательно** + KMS/HSM + ограничение ключей | **TLS обязательно**, mTLS для партнёров |
| Confidential‑Finance | **ENC@REST обязательно** + защита логов/бэкапов | **TLS обязательно**, сегментация каналов |

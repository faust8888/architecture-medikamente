# Движок классификации данных перед загрузкой в аналитическое хранилище (To‑Be)

## 1) Что проектируем

Нужен слой/движок, который **перед пакетной загрузкой** (batch ingest) в аналитическое хранилище:
- обнаруживает структуру входных данных (schema drift);
- классифицирует поля/наборы данных по классам конфиденциальности;
- проставляет теги и применяет политики (маскирование/псевдонимизация/кварыантин);
- ведёт lineage и метрики качества классификации.

## 2) Поддержка структурных изменений (schema drift)

Механизмы:
- **Schema Registry + versioning**: фиксируем версии схем источников/датасетов.
- **Schema inference** на входе: для «сырых» файлов/таблиц, где схемы не заданы.
- **Contract tests / DQ rules**: базовые проверки формата и обязательных полей; при несовместимости — в quarantine.
- **Active learning**: «неизвестные поля» помечаем как `unknown` и отправляем на разбор/дообучение.

## 3) Классификация и теги

Минимальные классы: `public`, `internal`, `confidential_pii`, `confidential_health`, `confidential_finance`.

Теги (пример):
- `data.class`
- `data.domain`
- `data.subject`
- `data.retention`
- `data.masking`

## 4) Организация слоёв в хранилище (lakehouse)

Рекомендуемая структура (с учётом того, что часть данных всё равно конфиденциальна):

- **Landing/Raw (restricted)**: сырой слой, доступ только data‑engineering/ИБ; ENC@REST; теги обязательны.
- **Quarantine**: данные, которые не прошли DQ/классификацию (или имеют высокий риск) — отдельный изолированный слой.
- **Curated (pseudonymized)**: основной слой для BI/ML — идентификаторы токенизированы, PHI/PII по умолчанию удалены/обобщены/агрегированы.
- **Sensitive enclave (если нужно)**: отдельная зона для строго ограниченных кейсов (например, мед.аналитика с PHI) с отдельными ключами, допусками и аудитом.
- **Semantic/BI marts**: витрины, которые потребляет бизнес; в идеале без PHI.

Дополнительные меры:
- **Row/column‑level security** в движке запросов/семантическом слое по тегам.
- **Watermarking/экспорт‑контроль**: запрет неконтролируемых выгрузок, DLP.
- **Lineage**: обязательная регистрация трансформаций (source→raw→curated→mart).

## 5) Метрики эффективности классификации (и как они помогают оптимизировать)

Точность классификации оцениваем как ML‑задачу + как операционную метрику качества данных:

- **Precision/Recall/F1** по классам (`confidential_pii`, `confidential_health` и т.д.).
  - важно отдельно отслеживать **False Negative** для `confidential_*` (самый опасный тип ошибки).
- **Coverage**: доля полей/датасетов, получивших уверенную классификацию (не `unknown`).
- **Drift metrics**: доля новых/изменившихся полей за период; скорость обработки drift.
- **Time-to-label**: время от появления нового поля до его корректной классификации (через human‑in‑the‑loop).
- **Policy compliance**: доля наборов данных, прошедших required controls (tagging, tokenization, encryption).
- **Throughput/Latency** pipeline: время обработки батча, SLA по загрузке.

Как оптимизируем:
- рост FN → усиливаем правила (pattern rules), дообучение моделей, повышаем консерватизм (fail‑closed) для новых полей;
- рост `unknown` → расширяем словари/регексы/feature extraction, улучшение интерфейса разметки;
- рост времени обработки батча → масштабирование воркеров, партиционирование, incremental processing.

## 6) Scalability и расширение

- **Горизонтальное масштабирование**: классификатор и DQ‑проверки как stateless workers (autoscaling).
- **Очереди/планировщик батчей**: контроль concurrency, backpressure.
- **Партиционирование**: по доменам/датам/источникам, чтобы рост объёма не «ломал» окна загрузки.
- **Кэширование результатов**: для повторяющихся схем/похожих полей.
- **Мультитенантность по филиалам** (если нужно): атрибут `branch_id` как часть политик доступа и партиционирования.

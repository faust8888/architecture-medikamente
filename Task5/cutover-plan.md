# Cutover‑план миграции (Parallel run)

## 1) Анализ ситуации и обоснование стратегии

### Текущее состояние (As‑Is)

- Данные пациентов и процессы ведутся вручную: Excel, сканы JPG/PDF на общем диске, Exchange/Outlook.
- Финансовый и складской контур — 1С (файловый режим) + интеграции с ККМ.
- Нет сквозного аудита и управляемого жизненного цикла данных; много копий и ручных переносов.

### Цели миграции (To‑Be)

- Единая платформа для записи/учёта/медкарты/интеграций + клиентский портал/мобильное приложение.
- Масштабирование (филиалы, рост команды, 5× рост данных).
- Усиление безопасности (Privacy by Design, шифрование, аудит).

### Выбор: Parallel run

**Плюсы для «Медикаменте»**
- Минимизация простоя: критичные процессы продолжают работать, пока новая платформа стабилизируется.
- Миграция «волнами»: по процессам (запись → документы → анализы → оплаты) и/или по филиалам.
- Можно системно выявлять расхождения данных и улучшать правила дедупликации/маппинга.

**Минусы/ограничения**
- Требуется синхронизация контуров и контроль расхождений.
- На период параллельной эксплуатации вырастут операционные затраты.
- Нужна дисциплина: запретить «теневые» Excel‑реестры в обход новой системы.

## 2) Роли и ответственность (упрощённо)

- **Migration Lead (TL/архитектор)**: владелец cutover‑плана, go/no‑go, координация.
- **Product Owner / Бизнес‑заказчик**: приоритизация процессов, приемка, коммуникации.
- **Data Lead**: маппинг данных, дедупликация, миграционные пайплайны, reconciliation.
- **SRE/DevOps**: окружения, релизы, мониторинг, бэкапы, rollback.
- **Security/ИБ**: IAM/MFA, KMS/сертификаты, аудит, DLP, контроль доступов.
- **Интеграции**: лаборатория, ККМ/фискализация, 1С (контракты/адаптеры).
- **Операционные владельцы процессов** (ресепшен/врачи/касса/бухгалтерия): UAT, обучение, контроль качества.

## 3) Cutover‑план (таблица)

Формат соответствует требованию задания:  
**Этап | Описание действия | Ключевые задачи | Ответственные | Время/Сроки | Риски и меры по снижению**

> Сроки ориентировочные. Для управления риском рекомендуется «волна 1» как MVP: **запись + уведомления + базовый реестр пациентов**.

| Этап | Описание действия | Ключевые задачи | Ответственные | Время/Сроки | Риски и меры по снижению |
|---|---|---|---|---|---|
| 0. Старт программы | Зафиксировать объём волны 1 | выбрать процессы волны 1; определить филиал/пилот; определить критерии успеха (SLO, качество данных) | PO, Migration Lead | Нед. 1 | риск расползания scope → формальная фиксация MVP + change control |
| 1. Инвентаризация | Каталог источников As‑Is | реестр Excel/папок/сканов/1С/почты; владельцы данных; оценка качества и объёма | Data Lead, владельцы процессов | Нед. 1–2 | «теневые файлы» не найдены → интервью, выборочные проверки, запрет новых выгрузок |
| 2. Классификация данных | Определить классы данных и допуски | PHI/PII/finance; кто имеет право читать/писать; правила маскирования | ИБ, Migration Lead | Нед. 2 | риск избыточного доступа → least privilege, MFA, ревизии |
| 3. Идентификаторы | Ввести единый `patient_id` | правила сопоставления (телефон+ДР+ФИО); обработка коллизий; журнал решений | Data Lead | Нед. 2–3 | риск «склейки» разных людей → conservative matching + ручной review коллизий |
| 4. Целевая платформа готова | Поднять To‑Be окружения | dev/stage/prod; сети/контуры; TLS; IAM/SSO+MFA; KMS; audit log; DLP базово | SRE/DevOps, ИБ | Нед. 2–4 | misconfig TLS/KMS → чек‑листы, staging‑репетиции, security review |
| 5. Интеграции (минимум) | Подключить критичные интеграции волны 1 | уведомления (SMS/Email/Push); базовая интеграция с лабораторией (если нужна в волне); подготовка адаптера к ККМ | Интеграции, ИБ | Нед. 3–6 | нестабильность партнёров → ретраи, очереди, договорённости SLA, фоллбек‑сценарии |
| 6. Миграционные пайплайны | Подготовить ETL/импорт | импорт реестра пациентов и записей; перенос документов как ссылок; протоколирование ошибок | Data Lead, SRE | Нед. 4–7 | плохое качество данных → DQ‑правила, quarantine, ручная доработка |
| 7. Rehearsal (репетиция) | Репетировать cutover на staging | прогон миграции на обезличенных/копиях данных; замер времени; проверка rollback | Migration Lead, SRE, Data Lead | Нед. 6–7 | риск «не влезли в окно» → оптимизация/батчинг, увеличить окно, пересчитать объём |
| 8. Обучение | Обучить пользователей волны 1 | инструкции, чек‑листы, что считать источником истины, как фиксировать инциденты | PO, владельцы процессов | Нед. 6–8 | саботаж/обходы через Excel → регламент, контроль выгрузок, поддержка на месте |
| 9. Parallel run старт | Включить новую систему для волны 1 параллельно | новая система пишет «основные сущности», старая остаётся как fallback; включить аудит/мониторинг | Migration Lead, SRE, владельцы процессов | Нед. 8 | расхождения данных → reconciliation отчёты, правила разрешения конфликтов |
| 10. Синхронизация (bi‑directional / one‑way) | Организовать период согласования | определить «master» для каждой сущности (например, записи — новая, бухгалтерия — пока старая); синхронизировать только нужное | Data Lead, PO | Нед. 8–10 | конфликт мастеров → явные правила mastership, запрет двойного ввода |
| 11. Нагрузочное тестирование | Проверить пиковые сценарии | запись в пиковые часы, массовые уведомления, отчёты, импорт‑джобы | SRE, QA, владельцы процессов | Нед. 8–10 | деградации → кэширование, очереди, limit/timeout, capacity |
| 12. Go/No‑Go‑гейт | Принятие решения на cutover | критерии: SLO, 0 P1 инцидентов, качество reconciliation, готовность support/rollback | Migration Lead, PO, ИБ | Перед cutover | субъективность → формализованные метрики и чек‑лист |
| 13. Cutover окно | Переключение «источника истины» для волны 1 | заморозка изменений в старом контуре для выбранных сущностей; финальная дельта‑миграция; переключение маршрутизации | Migration Lead, SRE, Data Lead | Ночь/выходной, 2–6 ч | риск простоя → pre‑sync, дельта‑миграция, обратимый feature flag |
| 14. Post‑cutover мониторинг | Усиленный мониторинг после переключения | war‑room; алерты; контроль очередей; контроль ошибок интеграций | SRE, ИБ, владельцы процессов | 24–72 ч | скрытые ошибки → повышенные алерты, ручные проверки ключевых сценариев |
| 15. План отката (если нужно) | Быстрый rollback | вернуть маршрутизацию на старый контур; отменить заморозку; сохранить журналы действий; анализ причин | Migration Lead, SRE | В течение 30–60 мин | потеря данных → журналирование, идемпотентность, фиксация «что успели записать» |
| 16. Завершение parallel run | Деактивация старого ввода | по достижению стабильности: запрет ввода в старом контуре; перевод на read‑only; архив | PO, ИБ, владельцы процессов | Нед. 10–14 | «хвосты» процессов → регламент, контроль прав, обучение |
| 17. Следующая волна | Расширение на EMR/Lab/Billing | повторить цикл для новых доменов/филиалов (волны 2+) | Migration Lead | По плану | эффект накопления долга → не растягивать parallel run, закрывать волны полностью |

## 4) Критические моменты (на что смотреть)

- **Mastership данных**: кто «истина» для записи/пациента/оплаты на каждом этапе.
- **Reconciliation**: отчёты расхождений, допустимые пороги, процесс исправления.
- **Интеграции**: лаборатория и фискализация должны иметь фоллбеки и очереди.
- **Безопасность как фактор производительности**: ABAC, аудит, DLP должны быть внедрены без блокировки основных сценариев (кэширование решений, асинхронная доставка логов).

## 5) Мини‑runbook cutover окна (пример последовательности)

- T‑24ч: объявление окна, freeze‑окно на изменения схем/релизов, проверка бэкапов.
- T‑2ч: включить war‑room, подтвердить критерии go/no‑go, проверить алерты «зелёные».
- T‑0: заморозка старого ввода для сущностей волны 1 (или перевод в read‑only).
- T+0…T+60м: дельта‑миграция + верификация reconciliation.
- T+60…T+90м: переключение маршрутизации (DNS/Ingress/feature flag).
- T+90…T+180м: smoke‑тесты ключевых сценариев, мониторинг очередей/ошибок.
- T+24–72ч: усиленный мониторинг, ежедневные отчёты расхождений.

## 6) План действий при проблемах (пример)

- **Рост ошибок записи/таймауты**: включить деградационный режим (упростить ответы, отключить тяжёлые отчёты), увеличить capacity, ограничить rate.
- **Расхождения данных**: приостановить дальнейший перевод, исправить правила сопоставления, повторить дельта‑перенос.
- **Инцидент безопасности**: остановить доступ, отозвать ключи/сертификаты, включить режим read‑only, расследование по audit‑логам.

# Отчёт: узкие места при миграции (монолит → современная архитектура)

Контекст (As‑Is): данные и процессы «размазаны» по Excel/сканам на общем диске, Exchange, 1С (файловый режим), одному серверу в офисе.  
Контекст (To‑Be): единая платформа с доменными сервисами, API‑контрактами, клиентским порталом/моб.приложением, интеграциями и аналитическим контуром.  
Цель отчёта: выявить причины узких мест (производительность/надёжность/качество данных) на этапе миграции и дать приоритетные меры.

## 1) Ключевые процессы и компоненты, затрагиваемые миграцией

- **Запись на приём / расписания**: ресепшен, клиентский портал, уведомления.
- **Медкарта / документы**: хранение PHI/PII, доступ врачей, аудит.
- **Анализы / лаборатория**: интеграция, файлы результатов, сопоставление пациенту.
- **Оплаты / ККМ / 1С**: корректность учёта, фискализация, отчётность.
- **Коммуникационные каналы**: внутренняя сеть, интернет‑периметр, почта, обмен файлами.
- **Серверное/облачное окружение**: вычисления, хранилища, бэкапы, мониторинг.
- **Бизнес‑логика**: правила записи, доступы, статусы, согласия, ретенция.
- **Данные**: перенос, дедупликация, нормализация, «сканы/Excel как БД».

## 2) Категории причин (для Исикавы) и потенциальные проблемы

### A. Инфраструктура

- **SPoF и недостаточная отказоустойчивость**: перенос с «одного сервера» без продуманного HA/DR → простои.
- **Сеть и межфилиальные каналы**: задержки/потери, нестабильный интернет в филиалах → деградация API/видеозвонков/доступа к EMR.
- **Неправильная sizing‑оценка**: 5× рост данных/пользователей, пиковые нагрузки записи → недооценка CPU/IOPS/throughput.
- **Нехватка наблюдаемости**: нет метрик/трейсов → долгое расследование деградаций.
- **Бэкапы/восстановление**: длительные окна бэкапа, отсутствие тестов восстановления.

### B. Программное обеспечение / Архитектура

- **Чаттеринг между сервисами**: слишком «тонкие» сервисы → много синхронных вызовов и высокая латентность.
- **Неправильные границы доменов**: сильные связи между EMR/Lab/Billing → каскадные деградации.
- **Ошибки в контрактном дизайне**: API «слишком широкие» (overfetching) → лишняя нагрузка и риск утечек.
- **Недостаточное кэширование**: справочники/расписания → рост нагрузки на БД.
- **Непродуманные фоновые задачи**: миграционные джобы и пересчёты конфликтуют с прод‑нагрузкой.

### C. Данные (качество, миграция, модели)

- **Низкое качество исходных данных**: Excel/сканы, разные форматы ФИО/дат/телефонов → ошибки сопоставления пациента.
- **Дубликаты и расхождения**: несколько «истин» (Excel ↔ 1С ↔ сканы) → нарушения целостности.
- **Неопределённые идентификаторы**: отсутствие единого patient_id → сложная дедупликация и риск «склейки» разных людей.
- **Сканы и вложения**: большой объём файлов, отсутствие метаданных → долгий перенос/индексация, проблемы поиска.
- **Lineage отсутствует**: сложно объяснить, откуда взялся показатель/запись.

### D. Интеграции и внешние контуры

- **Лаборатория**: нестабильность API/форматов, отсутствие контрактов и версионирования → падения пайплайна анализов.
- **ККМ/фискализация**: особенности протоколов/драйверов → инциденты при переключении.
- **1С**: файловый режим и ограничения интеграции → задержки/ошибки синхронизации.
- **Уведомления**: лимиты провайдеров SMS/Push, доставляемость → массовые ретраи и нагрузка.

### E. Безопасность и соответствие (как узкое место производительности)

- **Шифрование/аудит без архитектуры**: включение тяжёлых проверок на каждом запросе без кэша/батчинга → латентность.
- **Сложные ABAC‑проверки**: политика доступа обращается к нескольким источникам данных → задержки.
- **DLP/антивирус на файлах**: сканирование документов в реальном времени → узкие места загрузки/скачивания.
- **Ротация ключей/сертификатов**: ошибки в автоматизации → простои.

### F. Процессы и персонал

- **Недостаток компетенций**: микросервисы/observability/SRE/безопасность данных → неверные решения.
- **Отсутствие runbooks/SLA**: инциденты решаются долго, нет чётких RTO/RPO.
- **Сопротивление изменениям**: параллельный учёт в Excel продолжает жить → расхождения и ручные обходы.
- **Тестирование миграции**: нет нагрузочного/интеграционного тестирования → сюрпризы на запуске.

## 3) Рекомендации и приоритеты

Ниже — меры, вытекающие из диаграммы Исикавы. Приоритет: P0 (сделать до запуска), P1 (ранний этап), P2 (после стабилизации).

### P0 — критично до прод‑запуска

- **Стабильные границы доменов и контрактов**: чётко разделить Appointments/EMR/Lab/Billing/Documents; минимизировать синхронные зависимости.
- **Единый patient_id и стратегия дедупликации**: правила сопоставления (телефон+дата рождения+ФИО), ручной разбор коллизий.
- **Наблюдаемость**: метрики + логи + трассировки, SLO по ключевым сценариям (запись/поиск карты/загрузка анализа/оплата).
- **Нагрузочное тестирование**: пиковые окна записи, массовые уведомления, импорт/миграционные джобы.
- **План cutover и rollback**: критерии переключения, окно миграции, план отката.
- **HA/backup/restore**: настроить резервирование, протестировать восстановление (RTO/RPO).

### P1 — важно на ранней фазе миграции

- **Strangler‑подход**: поэтапный вывод функций из монолита/Excel, минимизация big‑bang.
- **Event‑driven интеграции** (где уместно): outbox + шина событий для уведомлений/аналитики.
- **Контрактное управление интеграциями**: версионирование API, consumer‑driven contract tests с лабораторией/фискальным контуром.
- **Оптимизация политик безопасности**: кэширование решений ABAC, батч‑аудит, асинхронная доставка логов.
- **Документы**: объектное хранилище + метаданные + фоновые задачи индексации/сканирования (не в запросе пользователя).

### P2 — после стабилизации (улучшения)

- **Оптимизация производительности**: кэширование справочников, read‑реплики, оптимизация запросов.
- **Автономность команд**: ownership доменов, runbooks, on‑call.
- **Data lineage и витрины**: зрелость каталога, quality gates, feature store.

## 4) Итог

Главные узкие места миграции — **качество и консолидация данных (Excel/сканы)**, **границы доменов и контрактов**, **наблюдаемость и готовность инфраструктуры**, а также **интеграции (лаборатория/ККМ/1С)**. Приоритетные меры (P0) направлены на снижение риска деградаций и простоев при переключении.
